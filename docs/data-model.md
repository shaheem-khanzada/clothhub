# ClothHub — Data model (Postgres)

ClothHub starts as a catalogue browser and grows into **Instagram for women's
fashion**: people follow each other, post outfits, tag products, ask "help me
choose", and the community's taste surfaces what is worth buying ("most
loved", "best on sale", "trending this week").

This document fixes the shape of the database so each later feature is new
tables in the right place, not a rework. Tables marked *(later)* are designed
here but are not created until their phase.

---

## Principles

1. **One namespace per domain.** Postgres schemas keep ownership clear and let
   a busy domain move to its own database later without renaming anything.

   | Schema | Owns | Written by |
   | --- | --- | --- |
   | `catalog` | brands, products, images, sizes, categories, prices | ingest job |
   | `ingest` | sync runs, source cursors, raw snapshots | ingest job |
   | `auth` | users, sessions, linked Apple/Google accounts *(phase 6)* | Better Auth |
   | `social` | profiles, follows, saves, collections, posts, votes, comments *(later)* | API |
   | `signals` | raw interaction events, daily rollups, scores *(later)* | API + jobs |

2. **IDs are UUIDv7.** They are time-ordered, so new rows land at the end of
   the index (fast inserts at scale, unlike random UUIDv4). They are safe to
   expose in URLs and generated by the API, so no database round trip is
   needed. Source systems' IDs are stored separately (`source_product_id`),
   never used as our keys.

3. **Every table has `created_at` / `updated_at` (`timestamptz`).** Things
   people may have saved or shared are **retired** (`retired_at`), never
   deleted, so saved lists and share links keep working.

4. **Money is an integer in the smallest unit** (`price_minor` paisa) plus
   `currency` (`'PKR'`). No floats.

5. **Typed columns for what we filter, sort or show; `jsonb` for the long
   tail.** For example, piece count, fabric and stitching are columns.
   Brand-specific extras go in `attributes jsonb`. Raw source payloads go in
   `ingest`, not in the catalogue.

6. **Counts are cached, not computed per request.** Likes, saves and
   followers live in small `*_stats` tables that are updated asynchronously.
   The hot row a list reads is never locked by every tap.

7. **High-volume events are append-only and partitioned by month.** They are
   rolled up into daily aggregates, and scores are recomputed by jobs.
   Screens read the scores, never the raw events.

8. **Constraints in the database:** foreign keys, `CHECK` (e.g.
   `price_minor >= 0`), unique keys for natural identities. The ingest job
   and the API can both be wrong; the database cannot.

## `catalog` — what we show

Shaped by the real scraper data. See `docs/scraper-data.md`: about 290k
products, 1.2M variants and 1.3M images across 99 brands.

```
brands ─┬─< products ─┬─< product_images
        │             ├─< product_variants      (size / colour / price / availability)
        │             ├─< product_components    (shirt / dupatta / trouser) (later)
        │             ├─< product_prices        (history, append-only)
        │             └── category_id ──> categories (tree)
        └─< brand_sources                       (where each brand's data comes from)
```

- **brands**
  - `id`, `slug` (unique), `name` (curated, not the scraper's domain-derived name), `website`, `logo_url`
  - `status` (`active` / `hidden`)
  - `audience` (`women` / `mixed` / `men` / `kids`): set per brand, and used as the prior when a product has no audience signal.
  - `currency` (`PKR` / `USD`): Shopify base currency. Some designers price in USD, and the scraper does not record it.
  - `claimed_by_org_id` *(later: brand self-service)*
- **products**
  - **Identity:**
    - `id`, `brand_id`
    - `source_product_id`, unique together with the brand. Scraper id `"{brandId}_{shopifyId}"`.
    - `sku`: the brand's code from the URL handle. Titles repeat across designs, so this is what tells them apart.
    - `slug`
  - **Text:** `name` (display), `short_name` (no piece count), `title` (brand's original), `description` (optional, about 7% empty).
  - **Classification:**
    - `audience` (`women` / `men` / `kids` / `unisex` / `unknown`)
    - `category_id`
    - Both are derived by ingest from `source_type` + `source_tags` + title. The raw values are kept, so products can be re-classified without re-syncing. The scraper's `type` has 3,010 distinct values.
  - **Price:**
    - `price_minor`, `price_max_minor` (variants can differ), `compare_at_minor` (null unless greater than the price), `currency`;
    - `discount_percent` — a **generated column**, so "best on sale" is a plain indexed query.
  - **Attributes:** `piece_count`, `stitching`, `fabric`, `color_families text[]`, `attributes jsonb`.
  - **State:**
    - `in_stock`, `retired_at`, `last_seen_at`
    - `first_seen_at`: drives "new arrivals", because source creation dates are unreliable when a brand migrates its store.
    - `source_published_at`
  - **Source:** `source_url` (the "Visit Brand" link).
  - **Search:** `search tsvector`, generated from name, brand, fabric and colour.
- **product_images**
  - `product_id`, `position`, `url`, `width`, `height` (the scraper provides both), `dominant_color` *(later: placeholders, colour filter)*
- **product_variants**
  - `product_id`, `source_variant_id`, `sku`
  - `size` (normalised: `S`, `M`, `5-6Y` …) and `size_label` (raw)
  - `color` (raw) and `color_family`
  - `price_minor`, `compare_at_minor`, `available`
- **product_components** *(later)*
  - `product_id`, `label` (Shirt / Dupatta / Trouser), `lines text[]`
- **product_prices**
  - `product_id`, `price_minor`, `compare_at_minor`, `observed_at`
  - Feeds "price dropped" alerts *(later)*.
- **categories**
  - `id`, `parent_id`, `slug`, `name`, `path` (materialised, e.g. `women/unstitched/3-piece`)
- **product_categories**
  - `product_id`, `category_id`

### Indexes planned for V1 queries

| Query | Index |
| --- | --- |
| Women's feed, newest first (in stock only) | partial `(audience, category_id, first_seen_at desc) where in_stock and retired_at is null` |
| Brand's products, newest / price sort | `(brand_id, audience, in_stock, first_seen_at desc)`, `(brand_id, price_minor)` |
| Best on sale | partial index `(audience, discount_percent desc) where compare_at_minor is not null and in_stock and retired_at is null` |
| Search | `GIN (search)` + trigram `GIN (name gin_trgm_ops)` |
| Ingest upsert | unique `(brand_id, source_product_id)` |

## `ingest` — how data arrives

- **sources**
  - `id`, `brand_id`, `kind` (`scraper` / `api` / `csv` / `manual`), `config jsonb`
- **runs**
  - `id`, `source_id`, `started_at`, `finished_at`, `status`, `stats jsonb` (seen / created / updated / retired / failed)
- **cursors**
  - `source_id`, `last_source_updated_at`
  - Incremental sync: each run only reads what changed.
- **raw_products** *(optional)*
  - The last raw payload per product plus a content hash.
  - Unchanged rows are skipped cheaply, and any product can be re-normalised without re-scraping.

New data sources (brand APIs, CSV uploads, a brand dashboard) are new `kind`s
here; the catalogue tables don't change.

## `auth` — accounts *(phase 6)*

Better Auth's tables: `users`, `sessions`, `accounts` (Apple / Google / email
links per user), `verifications` (email codes). App data references
`auth.users.id`; nothing else in `auth` is read by the app.

## `social` — people *(later)*

- **profiles**
  - `user_id` (PK), `handle` (unique, case-insensitive), `display_name`, `avatar_url`, `bio`, `visibility`
- **follows**
  - `follower_id`, `followee_id`, `created_at` — PK on the pair, plus an index on `(followee_id, created_at)`
- **saves**
  - `user_id`, `product_id`, `created_at` — the heart
- **collections**
  - `id`, `owner_id`, `name`, `visibility` (`private` / `unlisted` / `public`), `cover_product_id`
- **collection_items**
  - `collection_id`, `product_id`, `position`, `added_at`
- **posts**
  - `id`, `author_id`, `kind` (`outfit` / `look` / `help_me_choose`), `caption`, `visibility`, `created_at`
- **post_media**
  - `post_id`, `position`, `url`, `width`, `height`
- **post_tags**
  - `post_id`, `media_position`, `product_id`, `x`, `y` — products tagged on a photo
- **post_options** + **votes**
  - Help Me Choose: the options, and one vote per user per post
- **comments**, **reactions**
- **\*_stats**
  - `profile_stats` (followers, following, posts)
  - `post_stats` (votes, comments, reactions)
  - `product_stats` (saves, shares)

**Feeds** start as *fan-out on read*: query the posts of people you follow,
sorted by time and indexed on `(author_id, created_at desc)`. A precomputed
`feed_items` table is added only if reading gets slow.

## `signals` — taste of the community *(later)*

- **events**
  - Columns:
    - `id`, `occurred_at`
    - `actor_id` (nullable), `device_id`
    - `kind`: `view`, `save`, `unsave`, `share`, `click_out`, `vote`
    - `product_id`, `post_id`, `context jsonb`
  - **Range-partitioned by month.** Old months are detached and archived cheaply.
- **product_daily**
  - `product_id`, `day`, `views`, `saves`, `shares`, `click_outs` — rolled up by a scheduled job
- **product_scores**
  - `product_id`, `trending`, `loved`, `deal_score`, `computed_at`
  - Recomputed by a job from `product_daily`, with time decay for "trending this week".

These power **"most loved"**, **"trending"**, and **"best on sale"**, the last
being discount combined with community interest, so not just the biggest
percentage. If event volume outgrows Postgres, `events` and the rollups move
to ClickHouse; the `product_scores` table the app reads stays the same.

## Migrations

- Drizzle schema files live in `apps/api/src/db/schema/`, one per domain. Generated SQL goes in `apps/api/drizzle/`.
- Migrations are forward-only and run by `node dist/migrate.js` before each deploy.
- Changes are additive and backwards-compatible (add the column, deploy, backfill, then tighten), so a deploy never breaks the running version.
